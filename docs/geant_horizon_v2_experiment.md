# GEANT Horizon-v2 Pipeline — Implementation and Status

**Status:** isolated implementation with synthetic verification and one fixed raw-training-only Ridge screen. No model was trained, and no validation/test observations or arrays were read.

## Frozen question and boundaries

This pipeline follows `geant_protocol_v2_horizon_design.md`: forecast computed directed-link utilization at horizons 4 (one hour) and 96 (one day), using 672 history steps at 900 seconds per step. The official boundaries remain train `[0, 8020)` and validation `[8020, 9740)`. There is no test split argument, test filename constructor, test-array allowlist entry, test loader, or test evaluation branch in the new path.

The EWMA baseline is fixed at alpha 0.8 over the most recent five values, with a flat carry-forward forecast at both horizons. For horizon `h`, the residual target is `u[t+h,e] - S[t,e]`. Seasonal residual features are, in order, `u[t+h-96,e]-S[t,e]` and `u[t+h-672,e]-S[t,e]`; with the 672-step history their indices are 579 and 3 for h=4, and 671 and 95 for h=96. The graph model derives these features from history only.

## Data access and provenance

`phase9_geant/horizon_v2_data.py` constructs exact expected filenames from the fixed anchor `2005-05-04 15:00`, then performs one bounded `os.scandir` name enumeration. It validates the exact selected filenames in chronological order, detects missing/duplicate/malformed/off-cadence/unknown entries, and requests per-file metadata only for selected files. The train-only screen selected and checked 8,020 train files. The enumeration exposed 11,460 entry names, of which 3,440 valid nonselected GEANT matrix names (validation/test periods) were examined only as strings; no nonselected entry received a per-file `stat`, open, or parse. The selected filenames are passed to the reader-controlled cutoff API. The threshold is five times the median nonempty training-matrix demand, with the existing strict `>` rule and fixed per-demand limit. No validation/test matrix contents or metadata were accessed by the screen.

The new builder does not call `build_validity_v2.py`. The existing builder's train/validation mode still parses files after the training prefix, so it remains unsuitable for this experiment. The new builder's path generator does not construct those paths. It writes horizon-specific `history_{split}_h{4,96}.npy` and `target_{split}_h{4,96}.npy`, plus train/validation window-index JSON and metadata. Invalid observations remain NaN in the local link series and windows with invalid history or target are omitted rather than imputed. Intermediate future values are not required to be valid, matching the protocol; timestamp discontinuities from history through target reject a window.

The builder records selected filenames, parsed-source semantic fingerprints, the training-cutoff provenance, exact interleaved edge order and digest, local topology-file SHA-256, source-code hashes, build configuration hash, array shape/dtype/content hashes, window indices, and lifecycle status. The topology hash is only a local byte-identity check. Upstream dataset/topology provenance and the local source archive checksum remain unverified. Hashes do not prove runtime Python import identity.

New horizon arrays use an independent exact allowlist and do not alter `phase9_geant/split_access.py` or its legacy four-array allowlist. The loader verifies the artifact inventory, rejects test/unknown filenames, checks both train and validation split/window metadata, verifies array fingerprints, and rechecks the local topology identity/order before training. Path checks detect existing redirection components but are not race-free and are not a defense against a hostile local process or OneDrive/Windows filesystem races.

## Ridge signal screen

The implemented raw-source screen is training-only and consumes only parsed source indices `[0,8020)`. It pools link-origin examples without link IDs, uses fixed alpha=1 Ridge, and fits feature and residual standardization on the first 70% chronological eligible-origin prefix only. Holdout origins are taken from the remaining suffix only when they are at least 768 raw timesteps after the final fit origin; if this leaves no holdout, it fails instead of weakening the embargo.

For each horizon the fixed predictors are own daily seasonal residual, own weekly seasonal residual, mean neighboring current residual, and mean neighboring four-step change. Neighbor links share a router, include the reverse direction, and exclude the target link itself. All features are available by the forecast origin. EWMA is compared with EWMA plus the Ridge residual on the same selected origin/link pairs. The gate is `<0.5%` stop, `0.5% to <1%` review, and `>=1%` candidate-design review only. The 768-step gap is enforced in raw source indices. Invalid windows and the embargo leave fewer than 30% of eligible origins in the scored holdout.

### Fixed train-only Ridge result

The raw screen ran once on 2026-10-19 after filename preflight. It used 8,020 training matrices, fit-prefix standardization, Ridge alpha 1.0, 70% chronological eligible-origin fit prefix, and a 768-step embargo. The scored holdout contained all 72 links at each accepted origin; EWMA and Ridge therefore used identical pairs within each horizon.

The h=96 result supports only a candidate-design review; it does not authorize GNN training. The h=4 result remains STOP. The aggregate result artifact contains no per-origin or per-link errors, so concentration of the gain is unverified. This is an observed Ridge residual-screen benefit, not evidence that graph information caused the gain.

## Training interface

`phase9_geant/horizon_v2_experiment.py` defines the fixed configuration: seeds 42/123/2026, maximum 20 epochs, patience 4, Adam at 0.005, batch 32, hidden size 16, and SmoothL1 beta 0.001 applied to residuals in original utilization-ratio units. The final residual head starts at zero. Topology, identity, and deterministic degree-preserving shuffled adjacency use the same `SpatioTemporalLinkForecaster` operator and parameterization. Validation evaluation is gradient-free and selects checkpoints solely by the equal-horizon mean of per-horizon validation SmoothL1 losses. The checkpoint is reloaded strictly and hashed before final validation metrics are recorded.

The CLI requires exactly one explicit action (`--run-ridge-screen`, `--run-raw-ridge-screen`, or `--run-training`). This implementation does not auto-run any action. Training additionally requires a fixed seed and adjacency mode. Existing output paths are refused; outputs are segregated by adjacency mode and seed. Run manifests contain data/edge/source/config identities, training-only scaler statistics, histories, validation metrics, checkpoint hash, duration, lifecycle state, and the realized normalized adjacency hash/seed. The first-party source inventory now covers the experiment, data/window/path/validity/topology helpers, and the GNN package initializer and its imported model/dataset/preprocessing sources. These byte hashes describe files at run start; they do not establish which Python code was imported/executed and do not pin the Python, PyTorch, NumPy, or native-library runtime. A synthetic mock-model lifecycle test covers data-loader-free training/validation orchestration, validation no-grad behavior, and checkpoint finalization; it is not evidence of real-model training quality.

The training-only scaler now aggregates population mean/variance in bounded chunks rather than creating float64 copies and a concatenated copy of all overlapping train histories. The largest individual chunk is 1,000,000 float64 values (about 7.63 MiB before temporary centering storage). Based on the recorded train-window counts and float32 serialization, the two training history arrays alone represent about 1.44 GiB; the validation arrays add at most about 0.36 GiB from split-length bounds (the actual valid count is lower or equal). This is an arithmetic estimate, not a measured peak-RAM or runtime benchmark. The model has 1,506 trainable parameters by its dimensions, but each batch processes 32×72 independent 672-step GRU sequences; practical CPU runtime remains unmeasured.

## Verification and limitations

Synthetic verification completed on 2026-10-19: the focused horizon/model suite passed 57 tests; the wider relevant synthetic suite passed 136 tests with 5 skips; the two directory-junction tests separately passed using `_winapi.CreateJunction`. The 5 skips were directory-symlink cases (WinError 1314) or an unavailable symlink case, not passing junction evidence. `py_compile` passed for the new pipeline/model/test modules. Neither `pyflakes` nor `ruff` is installed, and no dependency was installed. The initial sandbox pytest attempt could not create three `tmp_path` fixtures; successful pytest runs used fresh basetemp directories under LocalAppData\Temp.

Not yet established: provenance/authenticity of the upstream raw source archive; empirically measured CPU training runtime and peak memory; actual training/validation window usability for GNN fitting; actual nontrivial shuffled adjacency for the 72-link production graph; and forecasting quality. The raw screen did establish train-period parseability and the h=4/h=96 window counts above. The 22-node, 36-undirected-link, 72-interleaved-directed-link structure is checked against the local topology bytes, but upstream provenance is not authenticated. Windows path checks remain path-based and are not race-free; prior synthetic junction tests do not establish OneDrive/cloud-placeholder semantics or protection against a hostile local process.

The current trainer consumes both fixed horizons in one shared multi-horizon optimization, and validation checkpoint selection gives equal weight to the h=4 and h=96 validation objectives. Because the screen classifies h=4 as STOP and h=96 only as CANDIDATE-DESIGN REVIEW, both the public `train_from_horizon_root` entry and low-level `_train_arrays` engine now fail closed before path/array work or output creation if this joint objective is requested. A separately reviewed horizon-specific protocol and implementation must resolve whether h=4 is excluded or explicitly retained as an auxiliary objective. No training was started here.

No result in this document supports forecasting improvement. The official test split remains sealed. Any final test evaluation would require a separate, independently approved frozen protocol and is outside this experiment implementation.
